# MyTimeTree — 微信小程序方案（对照 iOS 离线 App）

- 状态：**已搁置**（2026-08-16 用户决定专心做 iOS App，小程序不排期）
- 日期：2026-08-14（搁置说明 2026-08-16）
- 对照基线：已锁定的 **iOS only / 完全离线 / 密码+Face ID / iCloud 整库同步**

---

## 1. 一句话对比

| 维度 | iOS 离线 App（已锁定） | 微信小程序（本草案） |
|------|------------------------|----------------------|
| 运行时 | Capacitor WebView + 本机 SQLite | 微信小程序运行时（WXML/WXSS/JS） |
| 网络 | 日常可完全离线 | **默认必须有云端**（或云开发）；弱网可用缓存，难做到「纯离线」 |
| UI 复用 | **高**：现有 Portal HTML/CSS/JS 几乎原样进壳 | **低**：需重做页面；web-view 嵌套限制多，不建议当主路径 |
| 领域逻辑 | 须把 Python domain **移植到 TS**（与后端脱钩） | **可继续用现有 FastAPI**（推荐）；或再移植一份到云函数 |
| 登录/锁 | 家长密码 + Face ID（设备级） | 微信身份（openid）+ 可选家长密码；生物识别能力弱于 App |
| 同步/备份 | iCloud 整库文件 | 服务端 DB / 微信云开发；换手机靠账号，不靠 iCloud |
| 分发 | TestFlight → App Store | 微信公众平台审核；无苹果审核，但有类目/隐私/内容规范 |
| 用户获取 | 安装成本高 | 扫码即用，分享路径短 |
| 与现网 Portal | 同源 UI，双端分叉在「本地适配层」 | 另一套前端；后端可共用 |

**结论倾向**：小程序适合「要触达、要少安装」；iOS 适合「隐私、离线、本地资产树」。二者不是同一产品形态的薄封装，而是 **两条交付线**。

---

## 2. 为何不能「把 Portal 直接塞进小程序」

1. **不是任意 WebView**：主包必须是小程序组件体系；业务 `web-view` 需已备案域名，且能力/体验受限（导航、文件、生物识别、本地 SQLite 等）。
2. **没有 Capacitor 插件模型**：本地 SQLite、Keychain、Face ID、iCloud Documents 在小程序侧要么没有，要么换成微信云 / 服务端。
3. **树视觉**：现有大量 PNG + absolute CSS。小程序可用 image + 绝对定位复刻，但样式与手势要重调；复杂动画/滤镜可能降级。
4. **结息作业**：iOS 靠冷启动/回前台 catch-up；小程序靠 **打开时请求服务端补结**，或云定时触发（需一直有服务）。

因此：小程序 **不应** 复用「本地 TS domain + SQLite」这条 iOS 路径作为默认；更自然的是 **云端权威数据 + 小程序薄客户端**。

## 3. 推荐架构（小程序）

```
┌─────────────────┐     HTTPS      ┌──────────────────────────┐
│ 微信小程序 UI     │ ─────────────► │ 现有 FastAPI + SQLite/PG  │
│ (重写 WXML)      │ ◄───────────── │ 增加：微信登录 / 租户隔离   │
└─────────────────┘   JSON API     └──────────────────────────┘
        │                                      │
        │ 可选缓存                               │ 日终 job / 打开时 catch-up
        ▼                                      ▼
   wx.storage 只读缓存                      服务端权威流水与余额
```

### 3.1 必须新增的后端能力（相对当前单机 Portal）

当前 API 是 **全局 `current_account_id`、无会话**，不能直接多用户上线。小程序要上线至少要：

| 项 | 说明 |
|----|------|
| 微信登录 | `code → openid/unionid`，签发本系统 session / JWT |
| 租户模型 | `user_id`（家长）→ 多个 `account`（孩子）；所有 API 按 user 隔离 |
| 鉴权中间件 | 替换「任意人可调任意接口」 |
| HTTPS 部署 | 备案域名或云托管；小程序合法 request 域名 |
| 密码策略 | 开户/敏感操作仍可保留「家长密码」；与微信登录正交 |
| catch-up | 打开小程序时服务端补结漏日（逻辑已有，接到请求生命周期即可） |

可选：微信云托管 / 云开发数据库（改写存储层，工作量更大，一般不如继续 FastAPI）。

### 3.2 前端范围（小程序包）

对齐 Portal 现有 Tab/能力：

- 开户 / 多账户切换  
- 首页树 + 净资产 + 支出/借/还  
- 流水（分页）  
- 周/月分析  
- 每账户设置  
- 简单安全：进入敏感操作二次确认；可选「家长密码」锁设置页  

资源：树与挂件图可从 `static/portal/tree|ornaments` 压缩后放入小程序包或 CDN（注意主包体积 2MB 级限制 → 分包 / CDN）。

## 4. 工作量对照（粗估，单人熟悉栈）

单位：人天（含联调与基本测试，不含 App Store / 小程序长期打磨）。

| 工作包 | iOS 离线 App | 微信小程序（云端 API） | 说明 |
|--------|--------------|------------------------|------|
| 工程脚手架 | 3～5（Phase 0 已完成大半） | 1～2 | 小程序工具链更轻 |
| UI | 1～3（复用 Portal） | **8～15** | 小程序几乎重写；树布局最耗时 |
| 领域/数据 | **10～18**（Python→TS + SQLite） | **1～3**（接现有 API） | iOS 最重在移植；小程序最重在多租户 |
| 多用户/登录 | 0（本机单用户） | **5～10** | openid、会话、数据隔离、迁移 |
| 锁与生物识别 | 3～5（Keychain + Face ID） | 1～2（密码；SOTER 可选） | 小程序体验弱一档 |
| 同步/备份 | 4～8（iCloud 整库+冲突） | 已含在服务端；导出可选 1～2 | 模型不同 |
| 部署上架 | TestFlight/证书 3～7 + 审核不确定 | 域名/HTTPS/提审 2～5 | 小程序通常更快触达 |
| **合计（可试用）** | **约 25～45** | **约 20～40** | 量级接近，但 **风险与复用点不同** |
| **合计（可商店/正式）** | 再 + 打磨与审核 | 再 + 类目合规、隐私、性能 | — |

### 读法

- **总人天接近**，不是「小程序明显更省」。  
- iOS：**UI 省、领域移植贵、上架慢**。  
- 小程序：**领域可复用后端、UI 贵、必须先做多租户**。  
- 若强行「小程序也完全离线」：既要移植 domain，又要重写 UI，还缺少 iCloud 级同步，**工作量 ≈ iOS + 小程序 UI，最不划算**。

## 5. 产品差异（决策时要想清楚）

| 问题 | iOS | 小程序 |
|------|-----|--------|
| 数据在哪 | 用户手机（+ iCloud） | 你的服务器（责任与合规） |
| 没网能否支出/结息 | 能（本地 catch-up） | 基本不能可靠写 |
| 换 Android 家长 | 不做（当前锁定 iOS only） | 天然覆盖 |
| 隐私叙事 | 「数据在你手机里」 | 「微信里用的云服务」 |
| 与现有 `.local-data` | 可做导入（Phase 4） | 需「导入备份到云端账号」另做 |

若产品主叙事是 **本地时间资产保险箱**，小程序会稀释叙事；若主叙事是 **方便全家随手记一笔**，小程序更合适。

## 6. 分期计划（小程序，独立于 iOS）

假设：**不阻塞 iOS**；单独仓库目录 `miniprogram/` 或后续再建。

### Phase M0 — 可行性钉死（0.5～1 天）

- [ ] 确认：云端 FastAPI（推荐）vs 微信云开发  
- [ ] 确认：是否接受「无网不可用」  
- [ ] 注册/准备小程序账号、类目（育儿/工具类需对号）  
- [ ] 选定测试后端：现有部署改造 vs 新环境  

### Phase M1 — 多租户后端（约 5～10 天）

- [ ] `users` + 微信 `openid` 绑定  
- [ ] session/JWT；所有 portal API 挂 `user_id`  
- [ ] 废除或隔离全局 `current_account_id`  
- [ ] 打开会话时 catch-up  
- [ ] 最小管理：删除账号 / 导出备份（可选）  

### Phase M2 — 小程序 MVP UI（约 8～12 天）

- [ ] 登录 → 开户 → 首页树 + 支出/借/还  
- [ ] 流水列表  
- [ ] 设置（利率、派发等）  
- [ ] 分包与图片体积控制  

### Phase M3 — 分析与打磨（约 3～6 天）

- [ ] 周/月分析  
- [ ] 挂件与阶段视觉对齐 Portal  
- [ ] 错误态、空态、弱网提示  

### Phase M4 — 提审与合规（约 2～5 天）

- [ ] 隐私协议、用户协议  
- [ ] 合法域名、HTTPS  
- [ ] 提审材料与类目说明  

### 明确不做（首版）

- 小程序内嵌完整现有 HTML Portal（web-view 主路径）  
- 小程序纯离线 SQLite 权威库  
- 与 iOS iCloud 双向实时同步（若双端都要，需另立「云端同步协议」）

## 7. 与 iOS 路线的组合策略

| 策略 | 做法 | 适合 |
|------|------|------|
| A. 只做 iOS | 维持锁定计划 | 隐私/离线优先 |
| B. 只做小程序 | 停或缓 iOS；先多租户 + 重写 UI | 触达优先 |
| C. 双端，后端为源 | 小程序走云；iOS 仍可离线，另做「可选登录同步」 | 长期最完整，成本最高 |
| D. 先 iOS，后小程序 | 现在继续 Phase 1；小程序等 Xcode/App 稳定后再开 M0 | **推荐默认**：避免并行烧领域移植 + 多租户 |

**建议讨论点（请拍板）**

1. 小程序是否接受 **云端权威、无网只读/不可用**？  
2. 双端要不要共享同一套云账号，还是小程序与 iOS 各玩各的？  
3. 近期带宽：继续 iOS Phase 1，小程序仅保留本文档；还是插队做 M0/M1？

## 8. 风险清单

- 多租户改造碰现有单机假设，回归成本不低  
- 小程序审核对「未成年人/育儿工具」可能有额外说明要求  
- 主包体积与树图资源  
- 服务端可用性与备份责任（相对 iCloud 本地叙事）  
- 若同时推进 iOS 本地 domain 移植 + 小程序多租户，注意力会拆太散

## 9. 附录：API 面（小程序客户端需覆盖）

与现 Portal 对齐的主要路由（实现时以 `src/mytimetree/api/app.py` 为准）：

- `GET /api/portal/bootstrap` · `GET /api/portal/home`  
- `POST /api/accounts` · `POST /api/accounts/switch`  
- `POST /api/portal/spend|borrow|repay|deposit`  
- `GET|PATCH /api/settings`  
- `GET /api/ledger` · `GET /api/analytics/weekly|monthly`  
- 新增：`POST /api/auth/wechat`（或等价）及会话校验  

iOS 本地适配层是把上述路由落到 `MyTimeTreeLocal.handle`；小程序则是 **真实 HTTP 打到已鉴权后端**。
